# metasync v0 implementation plan

## Goal

Build an initial, usable web application in Go that lets the user:

- load two image sets:
  - left: images whose timestamps and GPS data may need correction
  - right: images that act as trusted metadata sources
- inspect extracted EXIF metadata for selected images
- browse both image sets in synchronized 15-minute timeline buckets
- detect likely timestamp-reset batches on the left side
- preview inferred timestamp/GPS corrections without mutating files
- view GPS locations for selected images on Leaflet/OpenStreetMap maps

This version is intentionally read-only. It should let us validate the UI, the alignment model, the metadata extraction pipeline, and the ergonomics of reviewing inferred fixes before we design actual file mutation.

## Constraints and selected stack

- Language/runtime: Go, using the globally installed toolchain.
- Web UI: Go templates plus embedded static assets.
- Reused libraries/patterns: use `github.com/jmoiron/monet` as the source of existing server/template/static patterns where useful.
- JavaScript: jQuery only, no TypeScript build step.
- Mapping: Leaflet + OpenStreetMap raster tiles.
- EXIF access: `github.com/barasher/go-exiftool`, with `exiftool` expected to be installed and available in `PATH`.
- Thumbnails: cached in `~/.cache/metasync/`, keyed by a hash of the source image's full path.

## v0 product shape

### Main workflow

1. User starts the app and provides two directories:
   - target directory for images to repair
   - source directory for trusted metadata images
2. App scans both directories recursively for supported image files.
3. App extracts metadata and builds a normalized in-memory model for each image.
4. App generates thumbnails on demand and reuses them from cache on later runs.
5. UI renders:
   - left image pane
   - right image pane
   - bottom metadata panel for each side
   - a shared timeline structure using 15-minute buckets
6. User clicks images to inspect:
   - filename/path
   - parsed timestamps
   - GPS coordinates if present
   - inferred batch/reset grouping on the left
   - previewed inferred corrections, when available
7. User can toggle a GPS view and see the selected image’s location on a Leaflet map in each pane’s metadata area.

### Explicitly out of scope for v0

- Writing timestamps or GPS metadata back to image files
- Bulk apply/undo workflows
- Editing metadata manually in the browser
- Background jobs across multiple users
- Authentication
- Database persistence

## Architecture

### Server-side

Single-process Go web app with these major responsibilities:

- HTTP server and routing
- directory scan + metadata extraction
- thumbnail generation and cache management
- in-memory session state for the currently loaded left/right datasets
- HTML rendering for the initial page
- JSON endpoints for image selection, timeline data, inferred matches, and thumbnail URLs

Suggested package layout:

- `cmd/metasync/`
  - app entrypoint and flag parsing
- `internal/app/`
  - server wiring, route registration, app config
- `internal/model/`
  - normalized image metadata structs and timeline batch structs
- `internal/scan/`
  - directory walking and supported-file filtering
- `internal/exif/`
  - exiftool wrapper and metadata normalization
- `internal/thumbs/`
  - thumbnail cache lookup/generation and filesystem layout
- `internal/timeline/`
  - bucket assignment, reset detection, overlap analysis
- `internal/infer/`
  - preview inference logic for proposed timestamp/GPS corrections
- `internal/web/`
  - handlers, view models, template glue, static asset serving

### Frontend

Server-rendered HTML with progressive enhancement:

- initial page rendered by Go templates
- jQuery for:
  - selection state
  - pane updates
  - timeline interactions
  - GPS view toggle
  - AJAX fetches for metadata details / preview inference
- CSS for:
  - fixed two-column layout
  - independently scrollable image panes
  - anchored bottom metadata sections
  - timeline bucket visuals

### Reuse from `monet`

The app should selectively borrow the parts of `monet` that reduce boilerplate:

- `chi` router patterns
- embedded templates/static file patterns
- `mtr` template registry if that proves simpler than hand-rolled template loading

We should not over-couple v0 to unrelated `monet` application concepts. Reuse the infrastructure patterns, not the whole app structure.

## Data model

### Image record

Each discovered image should be normalized into a struct roughly like:

- stable ID
- absolute path
- basename
- file size
- file modtime
- side: `left` or `right`
- thumbnail cache key
- thumbnail path/URL
- parsed capture timestamp, if available
- raw EXIF timestamp fields used to derive it
- GPS latitude/longitude, if available
- GPS altitude, if available
- camera make/model, if available
- batch ID for left-side reset grouping
- timeline bucket key
- flags:
  - has timestamp
  - has GPS
  - timestamp suspicious
  - GPS trusted

### Left-side batch model

We need a first-class concept for "timestamp eras" or reset batches on the left side.

Suggested structure:

- `BatchID`
- filename-ordered image range
- first observed timestamp
- last observed timestamp
- reset trigger index
- reason:
  - monotonic increase
  - timestamp jumped backward
  - missing timestamp split

### Preview correction model

For selected left images or batches, produce a preview object:

- selected anchor/match source image
- inferred corrected timestamp
- inferred GPS location
- confidence/explanation
- whether GPS is direct-copy, nearest-neighbor, or interpolated
- whether timestamp is anchor-based offset within a batch

## Metadata extraction plan

### Supported files

Start with common photo formats:

- `.jpg`
- `.jpeg`
- `.tif`
- `.tiff`
- `.png`

PNG likely will not contain useful EXIF often, but supporting it is low-cost if `exiftool` can inspect it.

Do not target HEIC in v0 unless it turns out to be necessary in the real corpus.

RAW support is likely valuable, but should be treated as a separate follow-up capability. The current candidate library is `https://github.com/seppedelanghe/go-libraw`.

### exiftool integration

Use `go-exiftool` to invoke `exiftool` once per scan batch, not once per field. Normalize a minimal set of tags into the internal model:

- `DateTimeOriginal`
- `CreateDate`
- `ModifyDate`
- GPS latitude/longitude and related refs
- camera make/model
- image dimensions if convenient

Implementation notes:

- Prefer a consistent timestamp precedence order.
- Keep the raw tag payload available for debugging.
- Record parse failures explicitly so the UI can show "missing" versus "unparseable".

### Timestamp normalization

Normalize parsed timestamps into Go `time.Time` values plus metadata about the source tag used.

Missing timezone data should not be treated as permanently unknowable. When GPS coordinates are available, we should be able to reconstruct likely timezone information from location and then interpret naive EXIF timestamps in that zone.

This likely requires an additional timezone-from-lat/lon lookup library or dataset, which is still an implementation-time dependency choice.

For v0, keep timestamps as parsed local-naive values in the normalized model, but structure the code so timezone reconstruction can be layered in later without changing the core image/timeline model.

## Timeline and alignment logic

### Shared 15-minute buckets

Create canonical bucket keys by flooring each known timestamp to a 15-minute boundary.

The UI should render both sides against the same bucket grid so visual overlap or lack of overlap is obvious.

### Left-side reset detection

Process left images in filename order and segment batches when:

- timestamps decrease sharply relative to the preceding image
- timestamps wrap to a default era or clearly older baseline
- timestamps disappear and later resume in a way that implies a reboot/reset boundary

Initial heuristic for v0:

- if `current_timestamp < previous_timestamp`, start a new batch
- keep a small threshold allowance if needed for camera jitter, but start simple first

### Alignment model

v0 should support inspection and preview, not auto-apply. A practical first version:

1. Build right-side trusted anchors from images with valid timestamps.
2. For left-side batches with timestamps:
   - preserve intra-batch relative offsets
   - let the UI preview alignment by choosing an anchor image
3. If overall left/right timelines show no overlap:
   - make that obvious in the UI
   - expose the batch structure so the user can pick a batch and inspect candidate anchor matches

### GPS inference model

For v0 preview:

- if a left image aligns closely to a right image with GPS, propose that GPS directly
- if a left image falls between two right images with GPS, preview simple linear interpolation by timestamp
- if only one nearby right image has GPS, preview nearest-neighbor copy with a lower-confidence label

We should surface the inference method in the UI so the user can judge whether the result looks believable.

## Thumbnail cache design

### Cache location

- root: `~/.cache/metasync/`

### Cache key

- hash the image’s absolute path
- use the hash as the thumbnail basename
- preserve an image extension like `.jpg` for browser compatibility

Example:

- source: `/photos/trip/day1/IMG_1234.CR3.jpg`
- cache key: `sha256(abs_path)`
- thumbnail path: `~/.cache/metasync/ab/cdef...thumb.jpg`

Use a shallow fan-out such as the first two hex characters as a directory prefix to avoid dumping all thumbnails into one directory.

### Cache validity

Do not rely on path hash alone. Store enough metadata to know whether a cached thumbnail is stale:

- source path
- source file size
- source modtime

Possible implementations:

- sidecar JSON manifest per thumbnail
- or encode a small metadata record in a SQLite/db file later

For v0, sidecar JSON is simpler and keeps the cache self-contained.

### Thumbnail generation

Recommended behavior:

- generate JPEG thumbnails
- constrain max width/height, for example `320x320`
- preserve aspect ratio
- generate lazily on first request, with optional up-front warmup endpoint later

Potential implementation path:

- first try Go-native decode/resize for formats Go can handle directly
- do not block v0 on HEIC support
- if RAW support becomes necessary, evaluate `go-libraw` for thumbnail generation and metadata-adjacent image decoding

This is one of the few areas where v0 may need a pragmatic fallback if Go-native decoding is insufficient for the real photo corpus.

## HTTP/UI plan

### Initial routes

- `GET /`
  - render the shell page
- `POST /load`
  - accept left/right directory paths, scan metadata, initialize current in-memory dataset
- `GET /api/timeline`
  - return bucketed left/right image summaries
- `GET /api/image/{id}`
  - return detailed metadata for one image
- `GET /api/infer/{id}`
  - return previewed correction data for one left image
- `GET /thumb/{id}`
  - serve or generate cached thumbnail

### Page layout

- top controls:
  - left directory input
  - right directory input
  - load/reload button
  - GPS view toggle
- main body:
  - left pane with timeline buckets and image thumbs
  - right pane with timeline buckets and image thumbs
- bottom of each pane:
  - fixed metadata panel
  - optional Leaflet map region when GPS view is active

### Interaction details

- clicking a thumbnail selects it and highlights it
- selection updates only that side’s metadata panel
- timeline buckets should remain visually aligned between panes
- batch boundaries on the left should be visually marked
- missing metadata should be explicit, not blank

## Leaflet + OpenStreetMap integration notes

For v0, use the standard Leaflet setup with the public OSM tile endpoint:

- Leaflet JS/CSS included in embedded static assets or vendored locally
- tile layer URL: `https://tile.openstreetmap.org/{z}/{x}/{y}.png`
- required attribution to OpenStreetMap

Operational notes:

- no OSM API key is required for the standard tile layer
- no account signup is required just to display standard OSM tiles in Leaflet
- production use must follow the OpenStreetMap Foundation tile usage policy
- attribution is mandatory

Practical implications for this app:

- v0 can work immediately without key management
- if usage grows or local usage becomes heavy, we should switch from the public OSM tile service to a dedicated provider or self-hosted tiles

## Implementation phases

### Phase 1: skeleton app

- initialize `go.mod`
- add `monet` dependency
- add `go-exiftool`
- create app entrypoint and HTTP server
- embed templates and static assets
- render a placeholder two-pane page

Exit condition:

- app starts locally and renders the shell UI

### Phase 2: directory loading and metadata scan

- implement recursive scan for supported image files
- integrate `go-exiftool`
- normalize image metadata into internal structs
- add `/load` and return scan results

Exit condition:

- app can load two directories and display file-backed image records

### Phase 3: thumbnail cache

- implement cache keying and manifest validation
- add thumbnail generation and serving
- render thumbnails in both panes

Exit condition:

- hundreds of images can load without full-size image fetches

### Phase 4: timeline and batch detection

- bucket images into 15-minute segments
- detect left-side timestamp resets in filename order
- render aligned timeline buckets
- visually mark batch transitions

Exit condition:

- user can understand overlap and reset structure at a glance

### Phase 5: selection and metadata panels

- implement click selection with jQuery
- add per-image metadata endpoint
- render detailed metadata into fixed bottom panels

Exit condition:

- clicking any image updates the corresponding metadata panel reliably

### Phase 6: GPS view

- add GPS toggle
- initialize one Leaflet map per pane
- place markers for selected images with GPS
- show "no GPS" state when unavailable

Exit condition:

- selected images with GPS display cleanly on the map

### Phase 7: inference preview

- add simple timestamp anchor preview for left-side batches
- add GPS nearest-neighbor / interpolation preview
- expose preview via API and metadata panel UI

Exit condition:

- user can inspect plausible proposed corrections without writing files

## Testing strategy

### Unit tests

- timestamp parsing and precedence
- 15-minute bucket assignment
- reset detection heuristics
- inference math for timestamp offsets and GPS interpolation
- thumbnail cache validation logic

### Integration tests

- scan sample fixture directories
- parse exiftool output into normalized models
- hit core HTTP endpoints with a test server

### Manual test dataset

Assemble a small local fixture corpus containing:

- left-side images with good timestamps
- left-side images with reset timestamps
- left-side images with missing GPS
- right-side images with good timestamps and GPS
- some mixed file formats

This fixture set will be important because the real value of the app depends on the shape of actual camera/phone metadata.

## Risks and follow-up questions

### Main risks

- RAW formats may complicate thumbnail generation and may require `go-libraw`
- EXIF timestamps may be missing timezone data, making cross-device comparison fuzzy
- GPS interpolation quality depends on how dense the trusted right-side photo coverage is
- public OSM tile usage is fine for local/dev use, but not something to assume indefinitely for heavier usage

### Questions deferred past v0

- exact UX for manually anchoring a left batch to a right image
- whether to persist app sessions or keep all state ephemeral
- how file mutation should work safely:
  - write in place with backups
  - write sidecars
  - export a review/apply script

## Definition of done for v0

v0 is complete when:

- the app loads two local image directories
- metadata is extracted through `exiftool`
- thumbnails are cached under `~/.cache/metasync/`
- both sides render in synchronized 15-minute timeline buckets
- left-side timestamp reset batches are visible
- selecting an image shows metadata in a fixed bottom panel
- GPS view renders Leaflet maps and markers for selected images with coordinates
- the app previews inferred timestamp/GPS corrections without mutating files
